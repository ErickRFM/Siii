## C32 contracts and boundaries

- POST /api/v1/admissions/register returns generic 202 requested; never id, email authority, raw proof or session. Existing accounts are neither overwritten nor duplicated. Registration is email-first: the stored placeholder is a random server-generated Argon2 hash, never a client-selected credential. A bounded optional legacy password field is ignored; email lookup and a unique expression index share lower(btrim(email)), preserving legacy IDs. Colliding historical canonical emails stop migration for explicit reconciliation; no automatic account merge.
- Verification proof: 32 random bytes; domain-separated SHA256 in profile; encrypted mail payload in the delivery outbox; expires after 30 minutes; profile lock makes consumption and replay exclusion atomic. Old email_verified_at alone is NOT mailbox evidence. Resend accepts email only, rotates proof and cancels old queued mail exclusively while mailbox_verified_at is null. Verify requires an explicit email-link confirmation and a NEW owner-chosen password (12–128 characters), refuses reuse of a legacy hash, replaces that hash and revokes all earlier applicant sessions atomically. No automatic session is issued. Already mailbox-verified profiles cannot be reset by resend; a dedicated applicant password-recovery flow is outside C32. Email scanners cannot activate an account by opening the link.
- The only raw-proof recipient is the mail delivery boundary and the user's email-link confirmation. It is never returned by registration/login/administrative JSON. The mail link uses a fragment; beforeInteractive bootstrap removes it before Next initializes, then hands it once to in-memory UI state. No token in DOM, localStorage, sessionStorage, server URL or query. Explicit confirmation POST consumes it; no automatic verification.
- Login creates a separate applicant session against the same applicant_profiles identity. Hashed server-side bearer, maximum eight hours, production __Host- cookie with Secure/HttpOnly/SameSite=Strict/Path=/ and no Domain. Rotation revokes previous sessions; logout revokes in the database and clears cookie. Institutional sessions cannot substitute for applicant sessions, nor grant applicant roles.
- Unsafe applicant methods require explicit same Origin and trusted Fetch Metadata. IP/account budgets use hashed keys and serialized rows. Unknown/unverified login has one response and performs dummy password verification. Registration/resend responses do not enumerate accounts.
- Application POST rejects applicantId and other mass assignment. Profile/session locks enforce current owner and revocation. Active institution, open cycle within dates, active same-tenant program/campus are checked in transaction. A cycle-row counter allocates unique deterministic ADM-cycleUUID-sequence folios. Repeated same-owner/cycle/program submission returns the previous result without another write/folio. It does not invent or change admission decisions, payments or enrollment rules.
- GET and SSR first use authorizeCapability(admissions.manage), including MFA. The final SELECT also uses institutionVisibility to recheck live session/version/grant/membership/tenant/factor. Institution-wide scope is required for the whole list; scoped grants do not collapse into tenant-wide roles. Guest/student/teacher/coordinator and foreign staff do not gain list access. SSR uses the dashboard's existing persistent shell, with no nested SiiAppShell.
- Public /admissions/institutionId contains active catalog/offer metadata and the applicant portal only, never a list of applicants. The existing components, styles and theme toggle are reused. Forms wait until session restoration finishes to avoid displaying stale identity.
- Every success affecting proof, sessions or application ownership is audited in its transaction. Applicant actor is recorded by target/after.applicantId; platform actor_user_id remains null because these are different actor types. Tokens/passwords and recipient payloads are excluded from logs/audit.
